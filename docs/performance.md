# Производительность и аудит

Локальная статистика и расчёт боя работают без ожидания zKillboard. После определения цели интерфейс получает первый рассчитанный вариант; остальные варианты дополняются в том же поколении запроса. Персональный фит и рейтинг загружаются отдельным сетевым потоком.

## Порядок обработки цели

1. UI передаёт цель расчётному потоку и одновременно ставит запрос пилота в сетевую очередь.
2. Расчёт читает подготовленную группировку или пользовательский кеш, рассчитывает первый вариант и отправляет его в UI.
3. Остальные варианты рассчитываются последовательно. Смена цели прерывает устаревшую работу между вариантами. Один уже начатый dogma-расчёт заканчивается обычным образом.
4. Кешированный персональный фит добавляется отдельной фазой. Сетевой поиск проверяет потери от новых к старым, сохраняет проверенные записи и заканчивается на первом подходящем фите. Используется тот же фильтр периода, PvP и исключений, что при чтении локальной базы.
5. Каждый ответ проверяется по поколению. Последующие публикации сохраняют свежую дистанцию, первый найденный персональный фит становится активным. Дополнение расчёта не сбрасывает выбранный вариант.

Интерактивный сетевой этап имеет бюджет 25 секунд, один HTTP-запрос — не более 8 секунд без повторов. Отмена проверяется до запросов, после ответа, во время чтения и перед кешированием. Уже выполняющийся блокирующий HTTP-вызов заканчивается ответом или тайм-аутом; SQLite также может ожидать блокировку записи. Поэтому бюджет не является строгой гарантией времени от клика до результата.

## Владение памятью и потоками

Пять постоянных рабочих потоков обслуживают расчёт, сеть пилотов, обновление базы, быстрый поиск и OCR. У каждого потока собственное изменяемое состояние; Engine и SQLite connection между потоками не разделяются. Каталог передаётся через `Arc`, активная SOLO-модель читается как неизменяемый снимок. Короткий `RwLock` нужен при получении и замене этого снимка.

Engine хранит до 256 результатов, кеш сравнения — до 64. Переполнение вытесняет одну старую запись. Производные характеристики собственного корабля хранятся отдельно одним элементом; ключ включает фит, навыки, импланты и бустеры. Числовой профиль боя хранит HP и резонансы трёх слоёв, без копии полного dogma JSON.

Импорт потерь, их принадлежность общей выборке и ревизии корпусов фиксируются одной SQLite-транзакцией. Персональные потери не меняют общие проценты. Фильтрация архива работает со ссылками на записи, JSON сериализуется прямо в gzip, исходный HTTP-буфер освобождается перед кешированием. При обучении SOLO после удаления дублей освобождается лишняя ёмкость векторов участников, корпусов и пар.

## Воспроизводимый замер

```sh
python3 scripts/benchmark_analysis.py \
  --executable target/release/eve-combat-assistant \
  --seed build/bootstrap-five-year/seed.sqlite3 \
  --fit tests/fixtures/kikimora-ammo.eft \
  --runs 3 \
  --output build/analysis-benchmark.json
```

Команда использует временные профили и подключает стартовую базу только для чтения. Каждый случай запускается в новом процессе. JSON содержит время первого вывода, полного расчёта, всего процесса и результаты анализа. В Linux дополнительно измеряется максимальный RSS через `/usr/bin/time`. Подробная диагностика включается самой командой `--fit-diagnostic`; сравниваемые сборки должны запускаться в одинаковых условиях.

Время расчёта начинается после загрузки каталога и открытия базы. Оно не включает ожидание следующего тика OCR, захват экрана, распознавание, очередь UI и ответ API. Для сопоставления точности нужно сравнивать результаты, исключив поля времени и RSS.

## Что проверено и что требует дальнейшей работы

Аудит 31.10.2026 охватывает путь цели, расчёт характеристик, HTTP, SQLite, OCR, диагностику и обучение SOLO. Регрессионные проверки воспроизводят откат неполного импорта, сохранение недавних кешированных фитов, раннюю публикацию вывода, отмену устаревших задач, независимый старт сети, выбор персонального фита и сохранение дистанции.

Остались следующие направления:

- Дальность оружия перебирает совместимые заряды полными dogma-расчётами. Сокращение этого перебора требует доказать эквивалентность зарядов по эффектам и дальности; отбор по названию небезопасен для точности.
- При нестандартных фильтрах история корпуса и нормализованные фиты одновременно находятся в памяти. Потоковая агрегация должна сохранять контекст соседних боёв для фильтра флотов.
- Просроченные записи HTTP-кеша не удаляются автоматически. Нужна небольшая фоновая очистка без `VACUUM` во время боя. Это рост файла на диске, а не доказанная утечка RAM.
- Подробная диагностика записывает файлы под общим mutex; отдельные события создаются и при выключенной записи. Большие области OCR создают несколько временных изображений. Нужны отдельные замеры с реальными областями захвата.
- Каналы событий не имеют жёсткого лимита. Ожидающие запросы расчёта схлопываются до последнего; для длительного зависания UI нужен отдельный тест очередей.
- Валидация собственного фита при сохранении настроек остаётся синхронной. Основные обработчики UI и запуск потоков имеют большую цикломатическую сложность и требуют постепенного разделения по обязанностям.

Постоянная утечка GDI/WinRT или Rust-памяти в этом аудите не установлена. Ограниченные кеши и высокий Working Set сами по себе её не доказывают. Для этого нужен длительный тест с измерением private bytes, commit и числа native handles при повторных сменах целей и захватах.

Для проверки структуры применены инструменты навыка [ub-mode](https://github.com/unclebob/ub-mode): crapper, dryer и mutator. Crapper выполнен без coverage, поэтому CRAP не измерен и общий порог не подтверждён. Кандидаты dryer проверены по смыслу: одинаковая форма обёртки над разными SQL-схемами не требует объединения. Точечная мутация границы кеша компилируется и обнаруживается тестом; это не оценка мутационного покрытия всего проекта.

## Результаты замеров 31.10.2026

Linux/WSL, release-сборки, одинаковая стартовая база и фит Kikimora из тестового примера; три новых процесса для каждого из восьми корпусов. Таблица показывает медианы. За исходную версию взят коммит `6cd8f0d`.

| Корпус | Первый вывод исходной версии, мс | Первый вывод, мс | Полный расчёт, мс |
| --- | ---: | ---: | ---: |
| Rifter | 1843 | 1102 | 1915 |
| Gnosis | 1086 | 809 | 1054 |
| Praxis | 1581 | 885 | 1543 |
| Megathron | 1107 | 246 | 1127 |
| Nighthawk | 1186 | 332 | 1183 |

| Marshal | 1152 | 254 | 1157 |
| Loki | 1723 | 1008 | 1762 |

Первый вывод готов на 24–78% раньше. Полное время расчёта изменилось незначительно; основной выигрыш даёт порядок выдачи. Все 24 полных отчёта совпадают по числовым результатам, включая советы, урон, резисты, скорость и дальность. Это локальный замер, без времени OCR и внешнего API.

Полное холодное обучение на 2 628 116 исходах: пиковый RSS снизился с 446 012 до 368 196 КиБ, примерно на 76 МиБ. Модели до и после совпадают целиком, включая коэффициенты и версию; в калибровке 140 071 пилот, собственный рейтинг в примере — 3162. Измерение относится к обучению, а не к постоянному расходу памяти оверлея.

Проверки: 142 теста Linux, 143 теста Windows, 8 тестов Python; Clippy с запретом предупреждений для обеих платформ. Инструменты анализа и замеры запускаются отдельно от пользовательского профиля.
